# ADR 0009: One admin login, password kept outside the repo

**Status:** Parked (ALPHA-119). Designed and built, then left out of the sprint scope: login stays open and is listed as a known risk. The code is saved outside the repo.
**Decision in one line:** login accepts only the admin account, whose password comes from a pipeline secret into Secrets Manager, and sign-up is closed.

## Context

`/auth/login` returned a valid token for any email and password, and `/auth/register` handed a token to anyone. The only screen is the admin dashboard, and the dashboard page had the admin password written in its code.

## Options

| Option | What it is | Result |
|---|---|---|
| **A. One admin account, password from a pipeline secret (chosen)** | `ADMIN_EMAIL` in the Helm values; the password is the `ADMIN_PASSWORD` GitHub secret, which Terraform writes to Secrets Manager (`eks-v2-<env>-admin-password`) and the gateway reads through an ExternalSecret | Closes "anyone can log in". The password is never in git, the same way works for dev, staging and prod, and it survives a full teardown because the GitHub secret lives outside AWS. |
| A2. Password written in the env config file | `ADMIN_PASSWORD: ...` in `envs/<env>/api-gateway.yaml` | Simplest, but anyone with repo access can log in, and staging and prod could not use it. |
| A3. Random password generated by Terraform | `random_password` stored in Secrets Manager | Nobody knows it unless they read it out of AWS, and a teardown makes a new one. Poor experience for a shared login. |
| B. A user table with hashed passwords | Sign-up, login against stored Argon2id hashes, roles | The right end state for customers. Needs a hashing library, account management and ownership checks across services; too much to do safely before the deadline. |
| C. An identity provider (Cognito or similar) | Login handled outside the app | More AWS cost and setup than one admin screen needs. |

## Decision

- The gateway compares the login with the admin account. It keeps only a SHA-256 of the password and compares in constant time.
- A wrong email and a wrong password both get 401 with the same message, as OWASP recommends.
- If `ADMIN_PASSWORD` is missing, the gateway still starts and refuses every login, so a late secret doesn't take the API down.
- Sign-up returns 403.
- The token carries `role: admin`. The gateway deletes any `X-User-Email` or `X-User-Role` a client sends, and sets them only from a checked token.
- The page shows a login box and keeps the token in memory only.
- The password is given to Terraform as an ephemeral variable (`TF_VAR_admin_password`, from the `ADMIN_PASSWORD` GitHub secret). Ephemeral means it is not saved in the plan file or the state. Terraform passes it to the secret through a write-only argument (`secret_string_wo`), so it is not in state either.
- The secret is encrypted with the project's KMS key. The gateway's pod identity may read it, and nothing else does.
- Each environment has its own secret and its own value. Staging and prod add the same ExternalSecret entry with their own `key` in their `envs/<env>/api-gateway.yaml`.

## Consequences

- Everyone who uses the dashboard shares one account and one rate limit, and the audit trail shows the admin, not a person.
- Login is limited to 20 tries a minute per IP. There is no per-account lockout, because it would let anyone lock out the only admin.
- Anyone who can read the GitHub secret or the Secrets Manager secret can log in. Share it the way any team credential is shared.
- The plan, apply and destroy workflows all need the `ADMIN_PASSWORD` secret, or Terraform stops with a missing variable.
- Deploy order: Terraform apply first (creates the secret), then the gateway sync. A gateway that starts before the secret exists runs but refuses every login.
- Orders are recorded against the admin's email, so emails go to the admin.
- Changing the password: update the GitHub secret, raise `secret_string_wo_version` in the secrets-manager module, and apply. Terraform only rewrites a write-only value when that version number changes. The gateway reads the value at start, so Reloader restarts it when the Kubernetes secret changes.

## How we know it works

Gateway tests: right password, email in another case, wrong password, other email, empty password, no password configured, sign-up closed, token claims, identity headers from a client. Breaking the password check makes the test fail. A browser test of the page: login box first, wrong password stays locked, right password loads the data, nothing in browser storage.

## Revisit when

Customers or more than one staff member need to log in. Then option B, with Argon2id hashes and ownership checks on orders and payments.
